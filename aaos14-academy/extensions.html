OEM Extensibility: System & Plug-in Services

Every carmaker needs its own services, policies and look — but forking AOSP makes every Android upgrade painful. AAOS offers a ladder of extension mechanisms, from “change a value in an XML overlay” to “add a brand-new system service”. This module explains each rung, when to use it and exactly how to wire it up.

⏱ 35 min read🎯 Intermediate → Advanced📂 packages/services/Car · frameworks/base · device/<oem>

6.1Extension points map

Micro tags such as [Config], [Plug-in] or [Policy] mark where an OEM can plug in without (or with minimal) changes to AOSP source. The guiding principle: prefer configuration over code, and plug-ins over forks.

6.3[Config] Configuration via overlays (RRO)

A Runtime Resource Overlay is a resource-only APK that replaces resource values (bool, integer, string, string-array, colors, dimensions, drawables, layouts) of a target package at runtime — without touching the target's code. AAOS is designed around this: most CarService behavior, occupant zones, plug-in lists and SystemUI layout are read from overlayable resources.

🎭
Analogy

An RRO is a sticky note on a printed manual. The manual (the AOSP APK) stays untouched; the reader (the resource system) sees your note on top of the original line. Remove the note and the original value is back.

Step by step: overlay CarService configuration

  1. Create the overlay modulee.g. device/oem/car/overlay/OemCarServiceConfigRRO/ with an Android.bp, an AndroidManifest.xml and a res/ folder.
  2. Declare the targetPoint <overlay android:targetPackage> at the package that owns the resources. If the target declares <overlayable> groups (see its res/values/overlayable.xml), also set android:targetName to the matching group.
  3. Override only what you needCopy the resource names (not the whole file) into res/values/config.xml with your values.
  4. Install itAdd the module to PRODUCT_PACKAGES. Static overlays (isStatic="true") are enabled at boot and cannot be toggled by users.
  5. Verify on the deviceadb shell cmd overlay list (look for [x] next to your package), adb shell cmd overlay dump com.oem.car.carservice.rro, and check the effective values in adb shell dumpsys car_service.
💡
Build-time overlays still exist

PRODUCT_PACKAGE_OVERLAYS / DEVICE_PACKAGE_OVERLAYS merge resources at build time instead of runtime. They work, but RRO modules are preferred: they are separate APKs, easy to inspect with cmd overlay, and do not require rebuilding the target. Note that resources in an updatable module (CarService) can only be customized through RROs.

6.4[Plug-in] CarService plug-in services (config_earlyStartupServices)

CarService contains a component called VendorServiceController. At startup it reads the config_earlyStartupServices array and, for each entry, starts or binds an OEM service as the right Android user, at the right moment, re-binding it if it crashes and following user switches. This is the official way to “plug” OEM services into the car's lifecycle without modifying CarService.

package/.ServiceClass#bind=bind|start|startForeground,user=system|foreground|all|visible|backgroundVisible,trigger=asap|userUnlocked|userPostUnlocked|resume
OptionValuesMeaning
bind (default start)bind · start · startForegroundbind uses Context#bindService — a bound service is restarted unless it keeps crashing; start / startForeground use startService / startForegroundService.
user (default all)all · system · foreground · visible · backgroundVisibleall = the system user and every visible user; system = headless user 0 only; foreground = foreground users only (unbound/stopped when the user is no longer foreground); visible / backgroundVisible = visible users / visible background users (MUMD passengers).
trigger (default userUnlocked)asap · resume · userUnlocked · userPostUnlockedasap may run before the user is fully loaded (the service must be directBootAware); resume = after resuming from suspend-to-RAM or suspend-to-disk; userUnlocked = when the user unlocks; userPostUnlocked = later, for non-urgent work.

Source: the documentation comment for config_earlyStartupServices in CarService res/values/config.xml (android14-release).

⚠️
Requirements & pitfalls
  • Ship the APK as a privileged system app (/product/priv-app or /system_ext/priv-app) with the permissions it needs allowlisted.
  • user=system services run as user 0 — they must not touch per-user data and should be directBootAware if they start before unlock.
  • Keep onCreate() fast: CarService starts many services during boot; heavy work belongs on a background thread or in a Garage Mode job.
  • Don't rely on being restarted with bind=start; use bind=bind for anything that must stay alive.

6.5[Policy] OemCarService — policy plug-in (Android 14)

Before Android 14, changing how AAOS makes certain decisions (for example the audio focus interaction matrix) meant forking CarAudioService inside CarService — painful now that CarService is an updatable module. Android 14 introduces OemCarService: CarService delegates selected policy decisions over a stable, versioned API to an OEM-supplied service.

How it works

  1. The OEM ships a privileged app with a service extending android.car.oem.OemCarService.
  2. An RRO sets config_oemCarService to that component.
  3. At boot, CarOemProxyService binds it (the service must be protected by android.car.permission.BIND_OEM_CAR_SERVICE).
  4. Car services ask it for decisions — e.g. CarAudioService asks the OEM audio-focus component to evaluate focus requests.

Fail-fast by design: if config_oemCarService is set but the service does not connect (config_oemCarService_connection_timeout_ms, 5 s default) or become ready in time, CarService crashes itself. Late answers to regular calls are ignored; a timeout on a critical call crashes both CarService and the OEM service.

Policy components (Android 14)

  • OemCarAudioFocusService — evaluate focus requests per audio zone.
  • OemCarAudioVolumeService — choose which volume group a volume key adjusts.
  • OemCarAudioDuckingService — decide which audio to duck.

Each is optional: if a component is not provided, the car audio service keeps its default behavior for that area.

Class and method names reflect the android.car.oem package in Android 14; the code is abridged — check the exact signatures in packages/services/Car/car-lib/src/android/car/oem/ for your branch.

🎭
Analogy

CarService is a referee who follows the official rulebook, but for a few specific calls (audio focus, volume, ducking) the league lets each team's appointed video assistant (OemCarService) make the decision. Calls the team didn't delegate stay with the rulebook. But once an assistant is appointed, the match cannot start without them — if they never show up, the referee stops the game (CarService restarts). Make your OemCarService fast and robust.

6.6[Fork] Adding a system service to system_server

⚠️
Last resort

This modifies frameworks/base. You will rebase it on every Android release, it can break CTS/GAS compliance if it leaks into public APIs, and it runs inside the most critical process on the device — a crash reboots the framework. Prefer [Plug-in], [Policy], [App] or [HAL] unless you truly need a platform-wide API available early in boot to many system components.

  1. Define the AIDL interfacePlace it in the framework (e.g. frameworks/base/core/java/android/oem/IOemDiagnostics.aidl) so both the service and the client manager can use it.
  2. Implement the serviceExtend com.android.server.SystemService, publish the binder in onStart() and enforce permissions on every call.
  3. Start it from SystemServerAdd a startService() call in the appropriate phase of SystemServer.java (usually startOtherServices()).
  4. Expose a managerWrite OemDiagnosticsManager and register it in SystemServiceRegistry so clients use context.getSystemService(OemDiagnosticsManager::class.java). Keep it @hide or @SystemApi — never public SDK.
  5. Label it in SELinuxDeclare a service type, add it to service_contexts and allow only the domains that should find it.
  6. Define the permissionAdd a signature|privileged permission (e.g. in an OEM framework-resource package) and allowlist the OEM apps that hold it.

Device-specific system policy goes in directories listed in SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS / SYSTEM_EXT_PUBLIC_SEPOLICY_DIRS rather than editing system/sepolicy directly.

✅
Lighter alternative: persistent privileged app service ([App])

Most “OEM system services” don't need system_server. A privileged app in /product/priv-app with android:persistent="true" (honored only for system apps) is started at boot, restarted if it dies, runs in its own process, and can expose an AIDL interface to other OEM apps protected by a signature permission — all without touching the framework. Combine it with config_earlyStartupServices when you need per-user lifecycle handling.

6.7[HAL] Vendor native services & HAL extensions

Hardware-facing extensions live on /vendor, behind a stable interface — exactly like the VHAL. Choose the right path:

It is a vehicle signal → VHAL vendor property

Seat massage, ambient-light scene, drive-mode switch: add a VENDOR-group property to your VHAL. Apps reach it through CarPropertyManager, with CarService enforcing permissions. No new interface, no new service. See the checklist in Module 05.

It is not a vehicle property → vendor AIDL service

High-bandwidth or streaming hardware (e.g. a DSP effects engine, a proprietary sensor) deserves its own @VintfStability AIDL interface on /vendor, registered with servicemanager and declared in VINTF.

  1. Define a stable AIDL interfaceAn aidl_interface with stability: "vintf" and vendor_available: true; freeze versions with m <name>-update-api / -freeze-api.
  2. Implement the service on /vendorA cc_binary with vendor: true, an init .rc file and a VINTF manifest fragment, registering vendor.oem.hardware.ambientlight.IAmbientLight/default.
  3. Let the framework depend on itAdd an entry to a device framework compatibility matrix (DEVICE_FRAMEWORK_COMPATIBILITY_MATRIX_FILE) so system-side clients may use it, marked optional if devices may lack it.
  4. SEPolicyLabel the service in vendor service_contexts and allow exactly the client domains (e.g. your privileged app) to find and call it.
  5. Consume itFrom a privileged app via the generated Java backend, or wrap it in a CarService plug-in service that applies policy and permissions before exposing it to other apps.

6.8Golden rules for OEM extensions

Config before code

If AOSP already reads a resource for it, overlay the resource. Search CarService's config.xml before writing a single line.

Plug in, don't fork

Early-startup services, OemCarService and privileged apps survive Android upgrades with little or no merge work.

Respect the Treble boundary

System ↔ vendor communication goes only through stable AIDL interfaces declared in VINTF — never through private libraries or files.

Least privilege, always

Protect every OEM service with a signature|privileged permission and a tight SEPolicy; vehicle control must remain gated by CarService.
