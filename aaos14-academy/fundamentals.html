Core Android Techniques

CarService, the VHAL client, every Car API callback and every plug-in service are built from the same few Android primitives: Binder for talking between processes, Handler / Looper / MessageQueue for scheduling work on a thread, and the process model that Zygote and init set up. Master these and the rest of AAOS stops looking like magic.

2.5.1Anatomy of an Android process

Every app — and CarService itself — is a Linux process forked from Zygote, running the ART runtime, with a handful of important threads. Knowing which thread runs your code explains most AAOS bugs: frozen UIs, ANRs, races in callbacks and deadlocks across services.

Main (UI) threadActivity/Service lifecycle callbacks, UI drawing, input, Handler(Looper.getMainLooper()) messagesNever block it — no disk, network or slow Binder calls. Input not handled within ~5 s → ANR.

2.5.2Binder IPC

Android processes are isolated by the kernel: they cannot read each other's memory. Binder is the kernel driver plus user-space libraries that let one process call a method on an object living in another process, as if it were local — while the kernel stamps every call with the caller's real identity.

🎭
Analogy

Binder is a company switchboard with a tamper-proof caller ID. You dial an extension (a Binder handle), the operator (the kernel driver) connects you to whoever answers at that desk (a binder thread in the server process), passes your message across, and tells the receiver exactly who is calling — you can't fake the caller ID. The phone directory is servicemanager.

Key concepts

Proxy & Stub

The client holds a proxy (IFoo.Stub.Proxy → BpBinder) that marshals arguments into a Parcel. The server extends the Stub (BBinder), whose onTransact() unmarshals the Parcel and calls your implementation. AIDL generates both.

One copy, one thread

The driver copies the transaction data once into a buffer that is mmap'd into the receiving process, then wakes one of the server's binder threads. The calling thread blocks until the reply arrives (unless the call is oneway).

Identity & security

Binder.getCallingUid() / getCallingPid() are set by the kernel, which is why CarService can trust them for permission checks. Use Binder.clearCallingIdentity() / restoreCallingIdentity() when the service must act as itself.

Limits & failure

The transaction buffer is about 1 MB per process, shared by all in-flight transactions → TransactionTooLargeException. If the remote process dies, calls throw DeadObjectException; register linkToDeath() to be notified.

2.5.3Handler, Looper & MessageQueue

Binder moves work between processes. Handler/Looper moves work between threads — and serializes it on one thread. The main thread of every Android app is simply a thread running a Looper.

MessageQueue

A queue of Messages ordered by due time (when, in SystemClock.uptimeMillis()). When nothing is due, the thread sleeps in the kernel (epoll) — no busy waiting.

Looper

Owns the queue and runs the loop on its thread: take the next due message, dispatch it to its target Handler, repeat. One Looper per thread: Looper.prepare() then Looper.loop().

Handler

The producer/consumer API bound to one Looper. post(), postDelayed(), sendMessage() enqueue from any thread; handleMessage() / the Runnable executes on the Looper's thread.

🎭
Analogy

A Looper is a single chef working through an order rail (the MessageQueue) sorted by when each dish is due. Waiters (Handlers on any thread) clip new orders onto the rail; the chef always cooks exactly one dish at a time, in due-time order. If one dish takes 10 minutes (a blocking call on the main thread), every other order — including the customer waving for attention (an input event) — waits. Wait too long and the customer walks out: that's an ANR.

Simulated time runs at 2× speed. Post work, add delayed messages, send a touch event, then try the heavy task and watch the input event wait until an ANR is raised.

Automotive gotcha: delays don't count deep sleep

Handler time is SystemClock.uptimeMillis(), which stops during deep sleep. A postDelayed(…, 1 hour) scheduled before the car enters Suspend-to-RAM fires one hour of awake time later — possibly days later. For wall-clock deadlines use AlarmManager, JobScheduler (Garage Mode) or handle SUSPEND_EXIT.

Sync barriers & async messages

The framework can insert a sync barrier so only messages marked asynchronous run — this is how Choreographer keeps frame rendering ahead of ordinary posts.

IdleHandler

Looper.myQueue().addIdleHandler { … } runs work when the queue has nothing due — handy for low-priority warm-up after startup.

Leaks

A delayed Message holds its Handler, which may hold an Activity. Remove pending work in onDestroy() (removeCallbacksAndMessages(null)) or use lifecycle-aware coroutines.

Coroutines are built on this

Dispatchers.Main dispatches through a Handler on the main Looper; withContext(Dispatchers.IO) moves work to a thread pool and back.

2.5.4Threading rules for AAOS code

Binder and Looper meet constantly in car code: a callback arrives from CarService on a binder thread, and the result must be shown on the main thread. These rules prevent most production bugs:

SituationWhere your code runsDo
Implementing an AIDL interface (server)Any binder thread, concurrentlyMake it thread-safe; return fast; offload long work to a worker Looper/Executor.
Receiving a callback from another processA binder thread of your processHandler(mainLooper).post { … } before touching UI.
Car API events (CarPropertyManager callbacks)The Handler/Looper associated with your Car object (main thread by default)Pass a worker Handler to Car.createCar(…) for high-rate signals so the UI thread stays free.
Calling a synchronous Binder methodThe calling thread blocks until the replyDon't do it on the main thread if the remote side can be slow (I/O, the vehicle bus, locks).
Calling a oneway methodReturns immediatelyNo return value, no exceptions from the remote; calls to the same Binder object are delivered in order.
Holding a lock—Never make an outgoing Binder call while holding a lock that incoming calls also need → cross-process deadlock.
🛠️
Catch it early

Enable StrictMode (disk/network on main thread) in debug builds, watch for Binder transactions on the main thread in Perfetto, and read ANR traces in /data/anr/ — they show exactly what the main thread was waiting on.

2.5.5Process model: init, Zygote & system_server

  1. Kernel → init (PID 1)init parses *.rc files, mounts partitions, sets system properties and starts native services (servicemanager, hwservicemanager, vndservicemanager, HALs such as the VHAL in class early_hal).
  2. ZygoteStarts the ART runtime and preloads common classes and resources once. Every Java process is then created by forking Zygote — fast startup and shared memory pages.
  3. system_serverThe first process forked from Zygote. SystemServer starts ~100 system services in boot phases (ActivityManager, PackageManager, WindowManager…), including CarServiceHelperService on automotive builds.
  4. CarService & persistent appsActivityManager starts persistent system apps — CarService (com.android.car) among them — which then binds to the VHAL and starts its plug-in services.
  5. AppsEach app is forked from Zygote on demand, given its own Linux UID (sandbox) and SELinux domain. Under memory pressure, lmkd kills processes by importance (cached → service → visible → foreground).
🎭
Analogy

Zygote is a pre-heated oven with dough already rolled out. Instead of baking each new pizza (app) from flour, Android takes the prepared base, adds the toppings (your app code) and serves it in a fraction of the time.

2.5.7System properties

System properties are global key–value strings managed by init, readable by any process and writable only by domains SELinux allows. They are used for build facts and simple configuration flags — not for runtime data exchange (use Binder for that).

PrefixBehaviorExample
ro.*Read-only after first set (build/boot facts)ro.build.version.release, ro.product.model
persist.*Survives reboot (stored on /data)persist.vendor.oem.telemetry.enabled
vendor.* / ro.vendor.*Owned by the vendor partition (Treble namespace)ro.vendor.oem.can.interface
othersRuntime, reset at rebootsys.boot_completed

adb shell getprop lists them; adb shell setprop sets one (if SELinux allows). New properties need an entry in property_contexts; for typed, versioned access across partitions, define them as sysprop APIs.

2.5.8Common pitfalls (and how AAOS amplifies them)

Blocking Binder call on the main thread

The remote side may be waiting on the vehicle bus or a slow ECU — your UI freezes. Use async APIs or a worker thread.

Forgetting CarService can restart

CarService is updatable and may crash/restart: handle ready = false in Car.createCar listeners and re-acquire managers.

Huge Parcels

Large lists or bitmaps over Binder hit the ~1 MB limit; use shared memory (SharedMemory, file descriptors) as the VHAL does with LargeParcelable.

Uptime-based timers across sleep

postDelayed and SystemClock.uptimeMillis() pause in Suspend-to-RAM; use wall-clock or elapsed-realtime APIs for real deadlines.
