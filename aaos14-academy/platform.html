11.3Boot & init sequence

A car boots like any Android device up to system_server. The difference is what happens around it: the MCU decides when the SoC powers on, vehicle HALs start early, and once the framework is up, CarService takes over to negotiate power with the vehicle and pick the right driver profile.

1 · Power-onMCU wakes the SoC · bootloader · verified boot
2 · Kerneldrivers · mount root · exec init
3 · initSELinux · *.rc · servicemanagers
4 · HALs & daemonsVHAL · EVS · power policy · watchdog
5 · system_serverZygote · framework · car helper
6 · CarServiceICarImpl · VHAL link · power ON
7 · User & homeinitial user · plug-ins · launcher

Phases run in this order; how long each takes depends on the SoC, storage and how much is started early. A rear-view camera must appear within about 2 s of selecting reverse, which is why it is often served by EVS or the MCU/RTOS long before Android's UI exists.

11.4Init, VINTF & product configuration

Four small files decide most of what the boot sequence above does on a given car. They are the first things to read when you bring up a new board.

① Product makefile

Inherits the car product, which declares android.hardware.type.automotive. That one feature flag is what makes system_server start the car stack at all.

② Init script (.rc)

Tells init how to start the vendor's Vehicle HAL: binary, user, groups and the class that decides when it starts.

③ VINTF manifest

Declares which HAL interfaces and versions the vendor provides, so the framework can find them across the Treble boundary.

④ CarService overlay

An RRO on CarService's config.xml: early-start plug-ins, occupant zones, optional features — no CarService code changes.

11.5Inside CarService: builtin & updatable

Since Android 13, CarService is split in two so Google can update it like a Mainline module. A small builtin part lives in system_server and has access to hidden framework APIs; the large updatable part ships in the com.android.car.framework APEX and runs in its own process.

Builtin (service-builtin)

Runs inside system_server. CarServiceHelperService starts CarService, forwards user lifecycle events and calls hidden framework APIs on CarService's behalf through car-builtin-lib. Changes only with a platform release.

Updatable (service)

Package com.android.car.updatable in the com.android.car.framework APEX. CarServiceImpl builds ICarImpl, which creates and initialises every car service. Can be updated without a full OTA.

⚠️
Rule of thumb

Because CarService is updatable, OEMs should not patch its code. Change its behaviour through overlays, plug-in services and OemCarService (Module 10) — otherwise every Google update of the module breaks your changes.

11.6Techniques AAOS is built on

AAOS adds very little new machinery. It reuses Android platform techniques and applies them to a vehicle:

Treble · Stable AIDL · VINTFFramework and vendor code are built and updated separately; only versioned AIDL interfaces cross between them. Binder IPCEvery hop — app → CarService → VHAL — is a Binder call with the caller's UID, so permissions can be enforced at each step. Mainline module (APEX)CarService ships in com.android.car.framework and can be updated independently of the platform. Headless system userUser 0 runs system services but never a display; each occupant gets a real Android user started on top of it. Runtime resource overlaysOEMs change configuration and theming of AOSP packages by overlaying resources instead of editing code. SELinux & permissionsCar permissions gate every API; SELinux limits which processes may even open the VHAL. Property modelMost vehicle data is one generic interface — typed, area-aware properties — instead of one HAL per feature. Multi-user multi-displaySeveral users run concurrently, each visible on its own display with its own audio zone and input.
