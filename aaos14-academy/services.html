Android Framework Services

CarService sits on top of the same framework every Android device runs. This module opens the big services inside system_server — Activity, Package, Window, Input and Power — and for each one explains what it owns, how a typical request flows through it step by step, and which dumpsys and cmd commands show its state on a real device.

⏱ 45 min read🎯 Intermediate📂 frameworks/base/services

12.1system_server & how a framework service works

Almost every framework service is a Java object living in one process, system_server, forked by Zygote at boot. Each service follows the same recipe: a class that extends SystemService (or is wrapped by one), a Binder stub it publishes to servicemanager under a short name (activity, package, window…), and a manager class in the app's process that hides the Binder calls. Hover a box to trace its connections.

① Apps: managers

context.getSystemService(ActivityManager::class.java) returns a manager. SystemServiceRegistry looks the binder up in servicemanager once and wraps it in the AIDL proxy (IActivityManager.Stub.asInterface).

② Services: each other

Inside system_server services do not use Binder to talk to each other. They call LocalServices.getService(ActivityManagerInternal.class) — a plain in-process Java interface, no IPC, no permission check.

③ Engineers: the shell

dumpsys <name> calls the service's dump(); cmd <name> calls its onShellCommand(). am, pm and wm are thin wrappers around cmd activity, cmd package and cmd window. See 12.8.

Startup order and boot phases

SystemServer.run() starts services in four batches, then walks every started service through numbered boot phases. A service may only use another service once the phase guarantees it exists.

🐕
The system_server watchdog

All framework services share one process. Watchdog checks that the main locks and handler threads of AMS, WMS, PMS and others make progress; if one is blocked for about a minute it dumps every thread's stack to /data/anr/ and kills system_server, which restarts the framework (a "soft reboot"). Look for *** WATCHDOG KILLING SYSTEM PROCESS in logcat.

12.2ActivityManagerService & ActivityTaskManagerService

ActivityManagerService (AMS) decides which app processes exist and how important each one is. Since Android 10 the activity and task half of it lives in ActivityTaskManagerService (ATMS), in the window manager package, because tasks and windows form one hierarchy. Both are registered in servicemanager: activity (AMS) and activity_task (ATMS).

Functionality & features

Processes & priorities

Starts processes through Zygote (ProcessList), keeps the LRU list, and computes each process's oom_adj and process state (OomAdjuster). lmkd kills the least important processes first when memory runs low.

Activities & tasks (ATMS)

ActivityStarter resolves and checks every startActivity(), places the ActivityRecord in a Task, applies launch modes and flags, and drives the lifecycle (onCreate … onDestroy) through ClientTransactions.

Services

ActiveServices handles startService, bindService and foreground services: permission checks, background-start limits, the 5–10 s startForeground() deadline and service ANRs.

Broadcasts & providers

BroadcastQueue delivers broadcasts to registered and manifest receivers. ContentProviderHelper starts provider processes and hands out provider binders.

ANRs & crashes

Detects unresponsive apps (input 5 s, foreground broadcast 10 s, foreground service 20 s), collects stack traces and shows the ANR or crash dialog. Records why each process died (ApplicationExitInfo).

Users, permissions, debugging

UserController starts, switches and stops users (used by CarUserService, 8.2). Also checkPermission() for UIDs, instrumentation and heap dumps.

Concepts: how AMS sees the world

ObjectRepresentsWhere you see it
ProcessRecordOne running app process: pid, uid, package list, process state, oom_adjdumpsys activity processes
ActivityRecordOne activity instance; also the window token for its windowsdumpsys activity activities
TaskA back stack of activities (what Recents shows)dumpsys activity recents
ServiceRecord / ConnectionRecordA started or bound service and each client binding to itdumpsys activity services

ContentProviderRecordA published provider and its connectionsdumpsys activity providers

The oom_adj score is what keeps the right apps alive: the foreground activity gets 0, a visible activity 100, a perceptible app (for example a foreground service playing music) 200, a service 500, the home app 600 and cached apps 900+. Binding raises the importance of the bound service to that of its client, which is why a bound service of a foreground app is not killed.

12.3PackageManagerService

PackageManagerService (PMS), service name package, is the device's database of installed apps. It parses every APK's manifest, gives each app its UID, installs and removes packages, and answers the most frequent question in the system: "which component handles this Intent?" Permission state and checks live in a separate PermissionManagerService that PMS delegates to.

Functionality & features

Boot scan

At boot it scans /system, /system_ext, /product, /vendor, /odm, APEXes and /data/app, and reconciles them with /data/system/packages.xml. That scan is a large part of boot time on first boot and after an OTA.

Install, update, uninstall

PackageInstallerService sessions receive the APK; PMS verifies signatures (APK Signature Scheme v2/v3/v4), checks updates keep the same certificate and versionCode rules, then commits.

Intent resolution

ComponentResolver holds every intent filter. resolveIntent(), queryIntentActivities/Services/Receivers() are what AMS calls on each startActivity, bindService and broadcast.

Package visibility

Since Android 11, AppsFilter hides other apps from an app unless it declares <queries>, holds QUERY_ALL_PACKAGES, or the other app interacted with it. Hidden apps simply look "not installed".

UIDs, permissions, features

Assigns app IDs (10000+), shared UIDs, grants install-time permissions and allowlisted privileged permissions; answers hasSystemFeature() from SystemConfig (/system/etc/permissions/*.xml), e.g. android.hardware.type.automotive.

Compilation & state

Triggers dexopt through ART Service after install and during idle maintenance; stores enabled/disabled components, default apps and per-user install state.

Concepts: where package data lives

ItemWhat it holds
/data/system/packages.xmlPersistent settings for every package: code path, app ID, flags, signatures, per-user state (installed, enabled, stopped). Written by Settings.
/data/system/packages.listOne line per app: package, UID, debuggable flag, data dir, SELinux info. Read by native code such as run-as.

12.4WindowManagerService

WindowManagerService (WMS), service name window, decides where every window goes, in what order it is stacked and which one has focus. It does not draw pixels: each window gets a SurfaceControl (a layer in SurfaceFlinger), the app draws into it, and SurfaceFlinger composes the layers onto the display.

Functionality & features

Window management

Adds and removes windows (addWindow, removeWindow), checks the window type is allowed for the caller and that the token is valid, computes frames and insets (status bar, navigation bar, IME, cutouts).

Z-order & hierarchy

Keeps one tree of WindowContainers per device; the position in the tree and the window type decide the layer order in SurfaceFlinger.

Focus & input

Chooses the focused window per display and publishes the list of input windows (bounds, touchable region, flags) that InputDispatcher uses to route touches and keys.

Displays & rotation

One DisplayContent per display — on a car: driver, cluster, passenger, rear seats. Handles rotation, size and density overrides.

Transitions & animations

Collects changes into transitions (Shell transitions) and lets the WM Shell in SystemUI animate them; manages starting windows (splash screens).

Others

Wallpaper, IME placement, screenshots, drag and drop, secure windows (FLAG_SECURE), window tracing for Winscope.

Concepts: the window hierarchy

ClassRole
WindowStateOne window: its attributes, frame, surface and input channel.
WindowTokenGroups windows of one owner; apps cannot add a window without a valid token (an activity's token is its ActivityRecord).
SessionOne per app process (IWindowSession); apps call addToDisplay, relayout, finishDrawing on it.
DisplayPolicyLayout rules for system bars and insets of one display.
Window typesTYPE_APPLICATION (1–99), sub-windows (1000–1999), system windows (2000+) such as TYPE_STATUS_BAR or TYPE_APPLICATION_OVERLAY (needs SYSTEM_ALERT_WINDOW).

12.5InputManagerService

InputManagerService, service name input, is a thin Java shell around a native pipeline in libinputflinger that runs on two threads inside system_server: InputReader turns raw kernel events into Android events, InputDispatcher delivers them to the right window. On a car the same pipeline also carries steering-wheel keys and rotary events injected by CarInputService (6.3).

Functionality & features

Devices

EventHub watches /dev/input/event*, loads key layout (.kl) and input device configuration (.idc) files and associates touchscreens with displays.

Reading & mapping

InputReader's InputMappers convert evdev codes to KeyEvents and MotionEvents in display coordinates (touch, keyboard, rotary, joystick).

Dispatching & ANR

InputDispatcher lets the policy intercept keys (power, volume, home), picks the target window, sends the event over an InputChannel and raises an ANR if the app does not answer in 5 s.

12.6PowerManagerService

PowerManagerService, service name power, decides whether the device is awake, the screen on and the CPU allowed to suspend. It combines wake locks, user activity and the charging state into one wakefulness value. On a car, CarPowerManagementService sits above it and drives screen and suspend from the vehicle's power state (4.1), but apps' wake locks still go through PowerManagerService.

Functionality & features

Wakefulness

AWAKE → DREAMING / DOZING → ASLEEP, per display group. Controls the display power state through DisplayManager's DisplayPowerController.

Wake locks

PARTIAL_WAKE_LOCK keeps the CPU running with the screen off; screen wake-lock levels are deprecated in favour of FLAG_KEEP_SCREEN_ON. Every lock is attributed to a UID (and WorkSource) for battery stats.

User activity & timeouts

Touches and keys reset the screen-off timeout; stay on while plugged in, attention and the device admin's maximum timeout are applied here.

Suspend

When nothing needs the CPU, it releases its suspend blocker in the native SystemSuspend service, which lets the kernel suspend. Also handles reboot and shutdown requests.

12.8dumpsys, cmd & the debugging toolkit

dumpsys is not a tool with built-in knowledge of each service. It only asks servicemanager for a binder and calls the generic dump() transaction on it; the service itself decides what to print. cmd works the same way with the shellCommand transaction. That is why the output format changes between releases — the source of the service's dump() is the documentation.

Cheat sheet

QuestionCommand
Which activity / window is in front?dumpsys activity activities | grep ResumedActivity · dumpsys window | grep mCurrentFocus
Is my service running, and who is bound to it?dumpsys activity services <pkg>
Why was my process killed?dumpsys activity exit-info <pkg> · dumpsys activity oom
Which permissions does my app have, what UID?dumpsys package <pkg>
Who handles this Intent?pm query-services|query-receivers|resolve-activity --brief -a <action>
Where do touches go?dumpsys input · getevent -lt
What keeps the device awake?dumpsys power · dumpsys batterystats
Why did the app freeze?/data/anr/ traces · dumpsys window lastanr · logcat -b events | grep am_anr
🔐
Permissions

A service's dump() requires android.permission.DUMP, and cmd usually requires the shell UID or root. Both are held by adb shell, so they work on user builds too, but an app cannot call them. A few dumps (/data/system/packages.list, /data/anr on user builds) need root or a userdebug build.
