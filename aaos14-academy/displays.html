Multi-Display & Occupant Zones

A premium car can have 5–7 screens. The question is not just “what to draw on which screen”, but “who owns this screen, where does touch input go, and which speakers play its audio”. The answer is the Occupant Zone.

Analogy

An occupant zone is like an airline seat map: each seat (zone) has its own screen, headphone jack and call button, and is tied to a specific passenger (Android user). The entertainment system must know “who pressed the button” to play the movie on the right screen and the right headphones.

3.3.3Input routing per zone

Input arrives from two sources that take different paths:

Touch screens (kernel input devices)

Each touch controller is an input device. The framework associates it with a display through an input port association (e.g. /vendor/etc/input-port-associations.xml or the display/inputTypes configuration). Touching RSE-L only produces events for zone 2's display.

Steering-wheel keys, rotary knobs (via VHAL)

These are not Linux devices but CAN signals. The VHAL emits HW_KEY_INPUT, HW_ROTARY_INPUT, HW_CUSTOM_INPUT properties with a target display type. CarInputService injects them into the matching display, or hands them to an app that registered via CarInputManager.requestInputEventCapture().

✅
Example

The driver presses ▶ on the steering wheel → CAN frame → VHAL HW_KEY_INPUT [ACTION_DOWN, KEYCODE_MEDIA_NEXT, targetDisplay=MAIN] → CarInputService → the driver user's media session, not the one belonging to the child watching a movie in the back.

3.3.4Multi-User Multi-Display (MUMD) — Android 14

Before Android 14 only one Android user ran in the foreground; passenger screens had to share the driver's user. Android 14 introduces visible background users: each passenger zone runs its own user, visible simultaneously on that zone's display.

AspectBefore Android 14Android 14 MUMD
Concurrent users1 foreground userDriver (current user) + visible background users

Audio / inputSharedFollows the user's occupant zone
⚠️
For app developers

Your app may run as several concurrent instances (one per user). Don't assume a single user; use Context.getDisplay() and the occupant zone instead of hard-coding Display.DEFAULT_DISPLAY. System-wide singletons must run as user 0 (the headless system user).
