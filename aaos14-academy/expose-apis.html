Exposing APIs with Intents & AIDL

One service, two kinds of clients. Service_A owns trip data. It offers a loose, Intent-based API to App_B (an ordinary app) and a typed, fast AIDL API to Service_C (a background service in another app). This module builds both step by step: contract, manifests, server code, client code, what happens inside the framework, and how to test each piece with adb.

⏱ 40 min read🎯 Intermediate📂 developer.android.com · AIDL

13.1The scenario & choosing a mechanism

All three components live in different apps, so every call crosses a process boundary through Binder. The difference is who is in the middle: an Intent always goes through ActivityManagerService, which resolves, checks and delivers it; an AIDL call goes directly from the client to the service once AMS has handed over the binder. Hover a box to trace its connections.

An API is a contract

Whatever the mechanism, write down four things before any code: names (actions, extras, interface), types and which fields are optional, who may call (a permission), and how it evolves (version number, append-only). Put the names in a small library both sides compile against — typos in action strings fail silently.

13.2Intent API, part 1: exposing it from Service_A

Service_A offers three Intent entry points. Each is a different Android component because each needs a different delivery guarantee:

💡
Why a receiver and not startService()?

Since Android 8, startService() on another app's service fails with IllegalStateException: Not allowed to start service Intent … app is in background whenever Service_A's app is idle — which is most of the time. An explicit broadcast always reaches a manifest receiver and starts the process. For short work, do it in the receiver with goAsync() (≈10 s budget); for long work, enqueue a job (WorkManager / JobScheduler) from the receiver, or have the client call startForegroundService() while it is itself in the foreground.

Step by step

  1. Write the contractPut every action, extra key, status code and permission name in a TripApi object in the shared trip-api library. Prefix every string with your package name so it cannot clash with another app's.
  2. Declare the permissionsIn Service_A's manifest, define READ_TRIPS (who may use the API) and SEND_TRIP_EVENTS (held only by Service_A, so clients can tell its events from fakes). Pick the protection level on purpose — see the table below.
  3. Declare the componentsMark the receiver and the activity android:exported="true" and protect each with android:permission="…READ_TRIPS". The intent-filter makes them discoverable with pm query-receivers / query-activities.
  4. Implement the receiverValidate every extra (never trust input from another app), call goAsync(), do the work on a background thread, answer through the client's PendingIntent, and call finish() in a finally.
  5. Send eventssendBroadcast(intent, READ_TRIPS): only apps holding the permission receive it. Implicit broadcasts reach only receivers registered at runtime, so clients listen while they are running.
  6. Document & versionNew optional extras are backward compatible; a changed meaning is a new action (…REQUEST_TRIP_SUMMARY_V2). Publish the contract with the library version.

13.3Intent API, part 2: calling it from App_B

Step by step

  1. Depend on the contractimplementation(project(":trip-api")) — or a published AAR. Never re-type action strings.
  2. Request the permission<uses-permission android:name="com.example.servicea.permission.READ_TRIPS"/>. With signature level it is granted at install only if App_B is signed with Service_A's key. Install Service_A first: a permission that is not defined yet cannot be granted.
  3. Make Service_A visibleSince Android 11, add <queries><package android:name="com.example.servicea"/></queries>. Without it, App_B cannot see Service_A: queries return nothing and Intents do not reach it.
  4. Build an explicit requestsetPackage("com.example.servicea") so no other app can receive the trip ID, and check with queryBroadcastReceivers() that someone will receive it — a broadcast with no receiver is dropped silently.
  5. Pass a reply PendingIntentPoint it at App_B's own non-exported TripReplyReceiver with an explicit component. Use FLAG_MUTABLE so Service_A can add result extras; because the component is fixed, Service_A cannot redirect it. Use FLAG_IMMUTABLE whenever the receiver does not need to fill anything in.
  6. Send it and handle the replysendBroadcast(request); the reply arrives in TripReplyReceiver as App_B (the PendingIntent's creator). Plan for no reply at all (Service_A crashed, was updated) with a timeout in your UI.
  7. Listen for events while runningRegister at runtime with RECEIVER_EXPORTED (required for other apps' broadcasts when targeting Android 14) and pass SEND_TRIP_EVENTS as the broadcast permission, so only Service_A can deliver TRIP_ENDED. Unregister when done.
  8. Open Service_A's UIstartActivity() with an explicit package; catch ActivityNotFoundException and SecurityException.

13.4AIDL API, part 1: define & build the interface

Service_C needs more than an occasional command: it queries trips often and wants every update pushed to it. That calls for a bound service with an AIDL interface. The .aidl files go into the same trip-api library as the constants, so Service_A (server) and Service_C (client) compile the identical interface. See 3.2 for how Binder carries the calls.

Step by step

  1. Pick the packageThe AIDL package (com.example.servicea.api) is part of the interface descriptor written into every transaction. Changing it later breaks every client.
  2. Define the dataA structured parcelable (parcelable TripSummary { … }) lets the AIDL compiler generate the class and its marshalling code — no hand-written Parcelable.
  3. Define the callbackMake it a oneway interface: the server never blocks on a slow or dead client.
  4. Define the service interfaceStart with a version method, then the calls. Mark parameters in (the default for most clients); add @nullable where null is a valid answer.
  5. Enable the buildGradle: buildFeatures { aidl = true } in the library (AGP 8 disables AIDL by default). Platform build: an aidl_interface module; both apps link its -java library.
  6. Freeze & evolveOnce a client ships, only append methods and parcelable fields. Never reorder, rename or remove — each method is identified by its position (transaction code), not by its name.
🧮
How a method is identified

The generated proxy sends FIRST_CALL_TRANSACTION + index for each method — getApiVersion is 1, getTripSummary 2, and so on. If Service_A reorders two methods, an old Service_C calls the wrong one with the wrong arguments. If a new client calls a method an old server does not have, it gets a RemoteException: call getApiVersion() first and skip newer methods.

13.5AIDL API, part 2: implement & expose it in Service_A

Step by step

  1. Implement the stubobject : ITripService.Stub() { … } inside a Service. Return it from onBind() — only for the expected action, otherwise return null.
  2. Remember the threadsStub methods run on Service_A's Binder thread pool (about 16 threads by default), several at once. Guard shared state with a lock or hand work to one worker thread. Keep each call short: the client is blocked until you return.
  3. Check the caller on every callThe manifest android:permission checks the client at bind time; re-check in each method with enforceCallingPermission(), and use Binder.getCallingUid() if answers depend on who is asking.
  4. Validate input, report errors as exceptionsThrow IllegalArgumentException, SecurityException, IllegalStateException or ServiceSpecificException — these are re-thrown in the client. Other exception types do not cross the process boundary: the server only logs them and the client gets a generic failure.
  5. Keep callbacks in a RemoteCallbackListIt links to each client's death and drops dead listeners automatically, and its broadcast API is safe while clients come and go.
  6. Declare and protect the serviceandroid:exported="true", android:permission="…BIND_TRIP_API", an intent-filter with …action.BIND_TRIP_API (see the manifest in 13.2).
  7. Make it debuggableOverride dump(): adb shell dumpsys activity service com.example.servicea/.api.TripApiService prints it, exactly like the framework services in 12.8.

13.6AIDL API, part 3: binding from Service_C

Step by step

  1. Request the permission and visibility<uses-permission> for BIND_TRIP_API and a <queries> entry for the bind action. Without either, bindService() returns false.
  2. Bind with an explicit IntentAction plus setPackage(); an implicit Intent throws IllegalArgumentException since Android 5. Use BIND_AUTO_CREATE so Android starts Service_A, and restarts it after a crash, while the binding exists.
  3. Convert the binderIn onServiceConnected() call ITripService.Stub.asInterface(binder). Check apiVersion before using newer methods.
  4. Never call on the main threadonServiceConnected() runs on the main thread, and every proxy call blocks until Service_A returns. Post calls to a worker thread (or use a coroutine on Dispatchers.IO).
  5. Register the callbackImplement ITripListener.Stub. Its methods run on Service_C's Binder threads — post to your own thread before touching state.
  6. Handle the three ways a binding breaksonServiceDisconnected(): Service_A's process died; Android re-binds and calls onServiceConnected() again, so register the listener again there. onBindingDied(): the binding will never come back (Service_A updated or force-stopped) — unbind and bind again. onNullBinding(): Service_A refused (returned null). Calls in flight throw DeadObjectException.
  7. Clean upUnregister the listener and unbindService() in onDestroy(). When the last client unbinds, Service_A gets onUnbind() and onDestroy().
  8. Multi-user (AAOS)A service running as the headless system user (user 0) binds Service_A in user 0. To reach the driver's instance, a privileged client uses bindServiceAsUser() with INTERACT_ACROSS_USERS (8.1).

13.8Variant: when Service_A is a system service

Everything above uses ordinary app components, so ActivityManagerService finds, starts and protects Service_A. If Service_A must be available very early in boot, to native code, or to every app through getSystemService(), it becomes a system service instead and registers its binder in servicemanager under a name — exactly like the framework services in 12.1.
