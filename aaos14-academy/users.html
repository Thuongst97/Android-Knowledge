Automotive Android User Profiles

A family car has many drivers. Each expects their seat position, mirrors, cluster layout, playlists and accounts the moment they get in. AAOS builds this on Android's multi-user system, extended with a User HAL so the vehicle itself — key fobs, seat modules, the cluster — takes part in every user operation.

⏱ 30 min read🎯 Intermediate📂 CarUserService · UserManagerService · User HAL properties

4.1How Android models users

Every Android user has its own user ID, its own /data/user/<id> storage, its own app data, accounts and settings. Apps are installed once but run as separate instances per user (UID = userId × 100000 + appId). AAOS adds one key twist: Headless System User Mode (HSUM).

User typeExample IDRole in the carNotes
Headless system user0Runs vehicle-wide services; never shown on a displayCarService, system services and user=system plug-ins live here. No launcher, no personal data.
Full user (driver)10The current (foreground) user on the driver's displaysCreated at first boot (setup wizard). Can be an admin who manages other users.
Full user (passenger)11, 12Android 14 MUMD: visible background users on passenger/rear displaysRun concurrently with the driver, each on their occupant zone's display.
Guest user13Valet, rental, a friend borrowing the carEphemeral: its data is wiped when the guest session ends.
🎭
Analogy

The car is a shared apartment. User 0 is the building's facility manager — always on duty, keeps the heating and electricity running, but has no bedroom of their own. Each driver or passenger is a tenant with a locked room (their storage) full of their own belongings (apps, accounts, preferences). A guest gets a hotel-style room that is cleaned out when they leave.

ℹ️
Why headless?

On a phone, user 0 is also the owner's personal user. In a car that would make the first driver “special” forever and would stop vehicle services during user switches. HSUM keeps vehicle-wide services running in user 0 while personal users come and go.

4.2User management architecture

Three layers cooperate on every user operation: the Android framework (which really creates/starts/stops users), CarUserService (car policy and orchestration) and the User HAL — a set of VHAL properties through which the vehicle can approve, veto or react to user changes.

User HAL propertyDirectionPurpose
INITIAL_USER_INFOAndroid → vehicle → AndroidAt boot, asks the vehicle which user to start (e.g. the user associated with the key fob that unlocked the car), or whether to create one.
SWITCH_USERBoth waysAndroid asks the vehicle to approve a switch (ANDROID_SWITCH → VEHICLE_RESPONSE), then reports completion (ANDROID_POST_SWITCH). The vehicle can also request a switch (VEHICLE_REQUEST).
CREATE_USERAndroid → vehicle → AndroidLets the vehicle allocate its own profile slot (seat memory, cluster profile) before Android finalizes the new user.
REMOVE_USERAndroid → vehicleNotification so ECUs can free that profile's stored data.
USER_IDENTIFICATION_ASSOCIATIONBoth waysAssociates the current user with identification mechanisms: KEY_FOB, CUSTOM_1…4 (e.g. phone key, face ID, driver card).
✅
Optional by design

The User HAL is optional. If the VHAL does not support these properties, CarUserService performs plain Android user operations and the vehicle is simply not consulted. Supporting them is what turns “Android users” into true vehicle profiles.

4.3User operations: add, switch, remove, start, guest

Car apps (Settings, a profile picker, an OEM welcome app) use the system API CarUserManager rather than UserManager directly, so that CarService can apply car policy and involve the User HAL. All operations are asynchronous and require signature|privileged permissions such as android.permission.MANAGE_USERS / CREATE_USERS.

  1. RequestThe UI calls CarUserManager.createUser() with a name and flags (admin or not, guest or full).
  2. Vehicle firstCarUserService sends CREATE_USER to the User HAL so the vehicle can reserve a profile slot (or refuse, e.g. when all seat-memory slots are used).
  3. Android creates the userUserManagerService allocates the next user ID, creates /data/user/<id>, installs system apps for the new user and applies default restrictions.
  4. ResultThe callback receives a UserCreationResult. Typically the UI then switches to the new user and runs a short setup flow (name, key fob association, preferences).
  1. RequestCarUserManager.switchUser() with the target user. CarUserService rejects invalid requests (unknown user, already current, a switch already in progress) and may apply OEM policy (e.g. no switching while driving).
  2. Ask the vehicleSWITCH_USER with message type ANDROID_SWITCH. The vehicle answers VEHICLE_RESPONSE with SUCCESS or FAILURE within a timeout.
  3. Android switchesActivityManager moves the old user to the background (or stops it), starts and unlocks the target user and shows its launcher.
  4. Tell the vehicle it's doneSWITCH_USER with ANDROID_POST_SWITCH; the vehicle broadcasts the new active profile so ECUs restore their settings.
  5. Lifecycle eventsListeners receive SWITCHING, UNLOCKING, UNLOCKED, POST_UNLOCKED; CarService re-binds user=foreground plug-in services.

See the full interactive flow, including the vehicle side, in 4.4.

  1. RequestCarUserManager.removeUser(). Removing the current user is handled by first switching to another user (or creating a new one if needed) — the car must always have a driver user.
  2. Android removesThe user is stopped, its storage and keys destroyed, accounts removed.
  3. Notify the vehicleREMOVE_USER tells ECUs to delete that profile's data (seat memory slot, cluster layout, key fob association).
⚠️
Keep at least one admin

Product policy usually forbids removing the last admin user, and resets to a fresh driver user rather than leaving the car without one.

With Android 14 MUMD, a passenger's user is started in the background and made visible on a specific display instead of switching the whole car.

Audio and input follow automatically: the occupant zone of that display is now bound to user 12. See Multi-Display → MUMD.

  • Guest user: created with the guest type, ephemeral — removed (and its data wiped) when the session ends. Ideal for valet/rental modes, often combined with user restrictions (no app installs, no account changes).
  • Maximum users: limited by framework configuration (e.g. config_multiuserMaxRunningUsers for concurrently running users) and by the vehicle's profile slots.
  • Restrictions: UserManager restrictions (DISALLOW_ADD_USER, DISALLOW_INSTALL_APPS…) let an admin limit what other profiles may do.
  • Pre-created users: to make “add profile” instant, products can pre-create users in the background and convert them on demand.

4.5Syncing the profile across AVN, cluster & ECUs

An Android user only owns what lives inside Android. A real “driver profile” spans many computers: the AVN/IVI (Android), the cluster VM, the seat and mirror modules, HVAC, HUD and the telematics backend. The key design decision is who stores each setting and what triggers the sync.

Profile identity mapping

Android userId (10, 11…) ⇄ vehicle profileId (1, 2…) ⇄ identifiers (key fob #, phone key, face ID)

The mapping is owned by the vehicle side (MCU/body domain or a profile ECU), established through CREATE_USER / USER_IDENTIFICATION_ASSOCIATION and used by INITIAL_USER_INFO at boot.

Try it: apply a profile to the whole vehicle

Boot with key fob → the right user from the start

Without a User HAL, the car boots into the last user and then switches — slow, and seats move only after Android is up. With INITIAL_USER_INFO, the vehicle tells Android which user to start first, while the seat module has already started moving before Android finished booting.

⚠️
Design pitfalls
  • Split brain: if a switch fails after the vehicle approved it, send the post-switch state for the user that is actually current so ECUs never show a different profile than Android.
  • Safety first: never move seats or steering while driving because of a profile change; the MCU must gate actuator recalls on vehicle state.
  • Privacy: keep personal data in the user's own storage; ECUs should only hold the minimum settings needed, tied to a profile ID — not names or accounts.
  • Timeouts: User HAL calls have bounded timeouts; a slow vehicle response must not block the driver from using the car.

4.6Lifecycle events & best practices for apps

System apps and plug-in services observe user changes through CarUserManager lifecycle listeners (with an optional event filter):

EventWhenTypical reaction
USER_LIFECYCLE_EVENT_TYPE_STARTINGUser is being startedPrepare per-user resources
…_SWITCHINGCurrent user is changing (has previous + new user)Save the old user's state, stop personal sessions
…_UNLOCKING / _UNLOCKEDCredential-encrypted storage is availableRead per-user preferences, push them to the vehicle
…_POST_UNLOCKEDUnlock processing finishedStart non-urgent work
…_VISIBLE / _INVISIBLE (Android 14)A user becomes visible on / leaves a displayMUMD passenger handling
…_STOPPING / _STOPPED, _CREATED / _REMOVEDStop, create, removeRelease resources, clean caches, update profile lists

The request/result classes and listener APIs shown on this page are Android 14 car system APIs; snippets are abridged — check android.car.user in your branch for exact signatures.

Never assume one user

Your app can run as several instances at once (driver + passengers). Keep state per user; never store personal data in user 0.

Put vehicle-wide logic in user 0

Things that must survive switches (telemetry, connectivity) belong in user=system plug-ins; per-person logic in user=foreground ones.

Go through CarUserManager

Calling UserManager/ActivityManager directly skips car policy and the User HAL — ECUs won't follow.

Design for failure

The vehicle can veto a switch. Show a clear message and keep the current profile fully usable.
