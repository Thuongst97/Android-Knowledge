9.4Best practice: threading with Handler & Looper

Every Android thread can own one Looper: an endless loop that takes Messages and Runnables from a MessageQueue and runs them one at a time. A Handler is the door into a specific Looper's queue. The main (UI) thread has a Looper already; for background work you create a HandlerThread, which is a thread that starts its own Looper.

Always name the Looper

new Handler() without a Looper is deprecated since API 30: it silently binds to whatever thread created it, or crashes on a thread without one. Write Handler(Looper.getMainLooper()) or Handler(thread.looper).

One thread, one owner

Posting all work for a component to one HandlerThread serializes it, so its state needs no locks. Hop back to the main Looper only to touch the UI.

Clean up on teardown

Call removeCallbacksAndMessages(null) and quitSafely() in onDestroy()/close(). A queued Runnable keeps its captured objects (often an Activity) alive until it runs.

Car APIs take your Looper

Car.createCar(context, handler, …) delivers its callbacks on that Handler's Looper (the main one when null). Passing a worker Handler keeps CarService reconnects and the work they trigger off the UI thread.

9.5Best practice: handling service connections

A bound service lives in another process that can crash, be updated or be killed for memory at any moment. A robust client treats “connected” as a state that comes and goes, not as something that happens once. The four ServiceConnection callbacks each mean something different:

CallbackWhen it firesWhat the client should do
onServiceConnectedThe service's onBind() returned a Binder.Wrap it with Stub.asInterface(), re-register listeners, reset the retry counter.
onServiceDisconnectedThe service process died. The binding stays active.Drop the proxy and show “unavailable”. Do not unbind: the system rebinds and calls onServiceConnected again when the service restarts.
onBindingDied API 26The binding can never reconnect (e.g. the service's package was updated or disabled).Unbind, then bind again, with backoff.
onNullBinding API 28onBind() returned null.Unbind: onServiceConnected will never come.

Unbind even when bind fails

bindService() returning false means the service was not found or you lack permission, but the connection is still registered. Call unbindService() either way, exactly once per bind.

Every remote call can fail

Wrap AIDL calls in try/catch (RemoteException). DeadObjectException is a subclass: the other process is gone and onServiceDisconnected is on its way.

Bind to the lifecycle that needs it

UI-only data: bind in onStart(), unbind in onStop(). Long-lived clients bind from a Service or the Application, never from a short-lived Activity.

Raw Binders need linkToDeath

A Binder you got some other way (e.g. returned by another AIDL call) has no ServiceConnection. Use binder.linkToDeath(recipient, 0) and unlinkToDeath() when done.

🚗
CarService already does this for you

For CarService itself you never write a ServiceConnection: Car.createCar(context, handler, CAR_WAIT_TIMEOUT_WAIT_FOREVER, listener) reconnects on its own and reports ready = false/true, as in the explorer above.

9.6Best practice: retry with backoff

A retry is a bet that the failure is temporary. Make that bet only for errors that are actually transient, wait longer after each failure, add jitter so that many clients do not all retry at the same instant after a CarService or VHAL restart, and stop when the component goes away.

FailureRetry?Reason
PropertyNotAvailableAndRetryException API 34YesThe VHAL returned TRY_AGAIN: ECU busy, bus temporarily off.
DeadObjectException / RemoteExceptionAfter reconnectThe service is restarting. Wait for onServiceConnected (or ready = true), then resend.
bindService() returned falseSlowlyThe package may not be installed or started yet at boot. Back off up to a long cap.
PropertyNotAvailableExceptionNoNot available in the current state (e.g. HVAC off). Wait for a state change event instead.
SecurityException, IllegalArgumentExceptionNoMissing permission or bad input: retrying gives the same answer.
⚠️
Retry only what is safe to repeat

Setting a temperature to 22 °C twice is harmless; “increase by one step” sent twice is not. Retry absolute, idempotent commands, or carry a request ID the service can deduplicate. Also cap the total time: a retry that lands after the driver changed their mind overwrites the newer choice.

9.7Best practice: implementing a service

The server side of IClimateService from 5.5. Two thread rules shape it: lifecycle methods (onCreate, onStartCommand, onBind) run on the main thread, and AIDL methods run on the Binder thread pool, several at once. So the service does no blocking work in lifecycle methods and funnels all state changes through one HandlerThread.

Check the caller in every method

android:permission on the service gates binding; enforceCallingOrSelfPermission() gates each call. Use Binder.getCallingUid() for per-caller rules, and wrap calls made on your own behalf in Binder.clearCallingIdentity() / restoreCallingIdentity().

Use RemoteCallbackList for listeners

A plain List of listeners leaks dead clients and breaks on equals(), because every call hands you a new proxy object. RemoteCallbackList keys by Binder and removes clients when their process dies.

Make listener interfaces oneway

Declare client callbacks oneway interface IClimateListener. Otherwise one slow or frozen client blocks your broadcast loop, and every other client, until it returns.

Pick the right start mode

Pure bound services need no onStartCommand. Started services return START_STICKY (restart, null intent), START_REDELIVER_INTENT (restart with the last intent) or START_NOT_STICKY. On Android 14 a foreground service must declare a foregroundServiceType.

🧭
Where should OEM logic live?

A privileged app service like this one suits OEM features that apps bind to. For logic that must start with CarService, or that extends system policy, see Module 10 · Which mechanism should I use?
