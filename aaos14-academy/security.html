Automotive Security & Sandboxing

On a phone, a malicious app can steal data. In a car, it could unlock the doors or distract the driver. That is why AAOS stacks several layers of defense from the app all the way down to the CAN bus.

⏱ 15 min read🎯 Intermediate📂 car-lib/…/Car.java · system/sepolicy

3.4.1Defense in depth

A request to “set 24 °C” must pass every layer below. An attacker would have to break all of them to send an unauthorized command to the vehicle.

1

App sandbox

Each app runs with its own UID and SELinux domain (untrusted_app / platform_app / priv_app). No direct access to devices or HAL services.

2

Car permissions in CarService

Every Vehicle Property is bound to read and write permissions. CarPropertyService checks the calling UID before anything reaches the VHAL.

3

SELinux & servicemanager

Only domains in hal_vehicle_client (in practice CarService) may find and call the IVehicle/default service. Regular apps are blocked at the kernel level.

4

VHAL validation

The VHAL checks that the property exists, the access mode, the areaId and the value range from VehiclePropConfig. Out-of-range values return INVALID_ARG.

5

MCU plausibility & hardware isolation

The MCU accepts only a predefined command set from the SoC and applies plausibility checks (e.g. never open the trunk while driving). A hypervisor separates IVI from the cluster.

6

Gateway firewall & SecOC

The gateway only lets the infotainment domain send whitelisted frames. Critical frames carry a MAC (AUTOSAR SecOC) so ECUs reject forged messages.

🎭
Analogy

It's like airport security: ticket check at the entrance (permission), baggage screening (SELinux), passport control (VHAL validation), the boarding gate only opens for the right flight (MCU), and the cockpit door is locked from the inside (gateway). Getting past one checkpoint doesn't get you into the cockpit.

3.4.2Car permissions

Automotive permissions use the android.car.permission. prefix and are exposed as constants in android.car.Car (e.g. Car.PERMISSION_CONTROL_CAR_CLIMATE = "android.car.permission.CONTROL_CAR_CLIMATE"). The protection level decides who can be granted each one:

⚠️
About CAR_INTENT_FORWARD

This name is not in the public permission list of android.car.Car in AOSP 14. If you meet it in a project, it is most likely an OEM-defined permission (e.g. com.oem.permission.CAR_INTENT_FORWARD). For vendor properties, the VHAL can assign custom permissions through the SUPPORT_CUSTOMIZE_VENDOR_PERMISSION property and the PERMISSION_VENDOR_* family.

3.4.4SEPolicy & VHAL access control

AOSP defines the HAL attribute hal_vehicle, split into two roles: hal_vehicle_server (the VHAL process) and hal_vehicle_client (CarService — domain carservice_app). The IVehicle/default service is labeled hal_vehicle_service; only valid clients may find it in servicemanager.

🔍
Debugging

When your VHAL cannot open its CAN socket, check adb logcat | grep avc. Add the minimal rule to your vendor policy (e.g. allow hal_vehicle_oem self:can_socket { create bind read write };) and never run permissive on a production vehicle.

3.4.5Hardware isolation & compliance

Hypervisor

IVI (AAOS) and the cluster run in separate VMs. Even if Android crashes or is compromised, the speedometer and warning lights keep working.

MCU as a controlled one-way gate

The SoC has no direct path to the chassis bus. The MCU forwards only permitted signals, with plausibility checks and rate limiting.

Verified Boot & HSM

Android Verified Boot (AVB) authenticates every partition; keys and certificates live in an HSM/TEE. A/B OTA updates are signed.

Regulation

UN R155 (cybersecurity management — CSMS), UN R156 (software updates — SUMS), ISO/SAE 21434 (automotive cybersecurity engineering). Mandatory for new vehicles in the EU and many other markets.
